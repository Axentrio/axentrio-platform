# Travel uncertainty splits three ways, by cause

A travel check can fail to produce an answer for reasons that look identical to a customer and are not remotely alike underneath, and the first draft of this plan treated them as one thing — fail open, confirm the booking, stamp `travel_check='unavailable'`. That is a decision to knowingly confirm an unverified drive, which is the defect the feature exists to prevent, and it is exploitable: a vague address or enough unique addresses to exhaust a tenant's cap degrades the gate for **every** customer of that tenant, and the owner discovers it standing in the wrong city. The opposite reflex, capture everything as a **Request**, is no better — a Maps outage would convert into a platform-wide manual-triage avalanche, and an owner drowning in Requests rubber-stamps them, which buys back exactly the wrongness the strictness was meant to buy off.

So the answer is neither, and it is not a single answer. **We cannot place the address at all** → a Request, which is what the platform already does with an out-of-area address (`CONTEXT.md` **Service Area**: *"fail-safe-to-request"*) and which already has an error code and prompt recovery written (`ADDRESS_NOT_PLACEABLE` at `modules/booking.module.ts:254`). **We placed it only to a town centre** (`approximate` precision) → ask for a postcode and retry once, using the same existing recovery, then fall through to the rule below. **Routes is unreachable, or the tenant's cap is exhausted, but coordinates exist** → refuse the slots that `couldReachWithin` proves impossible, confirm the slots that `certainlyReachableWithin` proves fine, and capture the undecided middle band as Requests. If Geocoding is *also* down, or a far-future booking's coordinates have aged past the 30-day deletion (ADR-0014) and cannot be re-resolved from `place_id`, there is nothing to reason over and the answer is a Request.

That third branch is load-bearing and worth stating plainly, because a reader will otherwise simplify it. The two haversine bounds in `api/src/contracts/travel.ts` are **proofs, not estimates**: at `PREFILTER_MAX_KMH` a straight line at motorway speed does not fit, so no routing answer could rescue the slot; at `PREFILTER_MIN_KMH` the worst plausible crawl still arrives, so no routing answer could condemn it. Only the band between them is opinion, and only that band becomes a Request. This means a plumber's next-door job still auto-confirms during a Google outage while a cross-province one is still refused — degraded mode is strictly better than the flat gap that shipped before this feature, and it never silently claims a verification it did not perform. The earlier draft of this branch confirmed the whole middle band at the flat gap; that was fail-open wearing a `travel_check` stamp, and `travel.ts:94` says so in terms — a `true` from `couldReachWithin` means *ask Google*, not *allow*.

**A Request must be acceptable, or this whole scheme is a trap.** `acceptRequest` (`booking-providers/internal.provider.ts:1764-1795`) re-runs `computeSlots` and `enforceBusinessCapacity`, which is exactly where the travel assert lives, so a travel-captured Request would be refused by the same gate that created it and the owner could never clear it. Acceptance therefore **skips** the travel gate and records the booking as owner-overridden, showing the estimated drive at the moment of accepting. This is consistent with the existing owner-decides principle (*"whether a job further out is worth doing is the owner's decision, not yours"*) and with the rule that owner-created portal bookings warn rather than block. Feasibility is a hard constraint against the *bot*, never against the person who owns the diary.
